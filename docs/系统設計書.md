## 1. 系统概述

### 1.1 目的

本系统面向派遣/SES 类 IT 企业，统一管理**社員情報**、**案件（プロジェクト）匹配与选考**、**取引先（客户）**、**人事日常业务**及**文件**等核心业务，支持按部门的数据权限隔离与 MFA 认证。

### 1.2 预期用户规模（公司上线规划）

| 部门/角色 | 人数 | 主要使用功能 |
|-----------|------|--------------|
| 营业（SALES_HEAD） | 约 10 人 | 社員查询/登记、案件・配属・匹配、取引先、文件上传 |
| 人事・事务（HR） | 约 2 人 | 社員维护、薪资编辑、人事业务、文件管理 |
| 管理员（ADMIN） | 1～2 人 | 用户管理、审计、全功能 |

合计系统账号约 **12～15 人**。当前单体架构（Docker + PostgreSQL）对该规模**足够**，无需额外水平扩展。

### 1.3 主要角色与职责

| 角色 | 代码 | 主要职责 |
|------|------|----------|
| 管理者 | ADMIN | 用户管理、审计日志、全数据读写删除 |
| 人事 | HR | 社員维护、薪资/人事编辑、人事业务、文件管理；**不可**访问案件域 |
| 事业部长 | DIVISION_HEAD | 所辖事业部及子部门社員的查看与编辑、案件与客户 |
| 部长 | DEPT_HEAD | 本部门社員的查看与编辑、案件与客户 |
| 营业 | SALES_HEAD | 社員登记/编辑、案件・配属・匹配、客户活动；薪资**仅查看**；数据范围排除人事部 |

> **已废止**：一般用户（USER）角色。V28 迁移删除该角色；仅含 USER 的账号将被禁用。

### 1.4 技术概要

| 层次 | 技术 |
|------|------|
| 前端 | React 19 + React Router 7 + Bootstrap 5 + Vite 6 |
| 后端 | Java 21 + Spring Boot 3.4.5 + Spring Security + JDBC（JdbcTemplate） |
| 数据库 | PostgreSQL 16（正式环境，Flyway 迁移） |
| 遗留 | SQLite（`sqlite` profile，仅开发遗留，本番不使用） |
| 部署形态 | 单体 JAR，内嵌 Tomcat；静态前端打包于 `classpath:/static/` |
| 容器化 | Docker Compose（`postgres` + `app`），支持 Windows / Linux 服务器 |

## 5. 认证与权限设计

### 5.1 认证方式

- **Session 认证**：登录成功后服务端 HTTP Session，Cookie 维持（`SessionCreationPolicy.IF_REQUIRED`）
- **MFA（TOTP）**：可选启用，支持恢复码
- **公开 API**：`/api/auth/login`、`/api/auth/mfa/*`
- **401 处理**：前端 `api.js` 自动登出并跳转 `/login`
- **CSRF**：API 场景下已禁用（`csrf.disable`）；依赖 Session Cookie 同源策略

权限函数前后端对应：

- 前端：`frontend/src/auth.js`
- 后端：`backend/.../auth/SecurityService.java`

### 5.2 角色定义

| 角色代码 | 日文名称 | 固定所属部门 |
|----------|----------|--------------|
| ADMIN | 管理者 | — |
| HR | 人事 | 人事部 |
| DIVISION_HEAD | 事業部長 | 自选（事业部） |
| DEPT_HEAD | 部長 | 自选（部门） |
| SALES_HEAD | 営業 | 営業部 |

用户管理可选角色：`ADMIN`, `HR`, `DIVISION_HEAD`, `DEPT_HEAD`, `SALES_HEAD`（不含 USER）。

### 5.3 权限函数一览

| 函数 | 含义 | 角色 |
|------|------|------|
| `canWrite()` | 社員登録・編集 | ADMIN, HR, DIVISION_HEAD, DEPT_HEAD, **SALES_HEAD** |
| `canDelete()` | 社員削除 | ADMIN |
| `canViewSalary()` | 薪资・人事 Tab 查看 | ADMIN, HR, DIVISION_HEAD, DEPT_HEAD, **SALES_HEAD** |
| `canWriteSalary()` | 薪资・人事 Tab 编辑 | ADMIN, HR, DIVISION_HEAD, DEPT_HEAD（**营业只读**） |
| `canViewProjectFeatures()` | 案件・配属 查看 | 全登录用户 **除 HR** |
| `canWriteProjectFeatures()` | 案件・配属・候補者 编辑 | ADMIN, DIVISION_HEAD, DEPT_HEAD, **SALES_HEAD** |
| `canViewFiles()` | ファイル管理 查看 | 全登录用户 |
| `canWriteFiles()` | ファイル 上传/删除 | ADMIN, HR, DIVISION_HEAD, DEPT_HEAD, SALES_HEAD |
| `canViewClientEvents()` | 取引先・顧客活動 查看 | ADMIN, HR, SALES_HEAD, DIVISION_HEAD, DEPT_HEAD |
| `canWriteClientEvents()` | 取引先・顧客活動 编辑 | 同上 |
| `canManageHrOps()` | 人事業務画面 | ADMIN, HR |
| `canManageUsers()` | 用户管理・审计 | ADMIN |

### 5.4 权限矩阵（功能域）

| 功能域 | ADMIN | HR | DIV_HEAD | DEPT_HEAD | SALES |
|--------|:-----:|:--:|:--------:|:---------:|:-----:|
| 社員写入 | ✓ | ✓ | ✓ | ✓ | ✓ |
| 社員删除 | ✓ | — | — | — | — |
| 薪资查看 | ✓ | ✓ | ✓ | ✓ | ✓ |
| 薪资编辑 | ✓ | ✓ | ✓ | ✓ | — |
| 案件・配属 查看 | ✓ | — | ✓ | ✓ | ✓ |
| 案件・配属 编辑 | ✓ | — | ✓ | ✓ | ✓ |
| ファイル 查看 | ✓ | ✓ | ✓ | ✓ | ✓ |
| ファイル 上传/删除 | ✓ | ✓ | ✓ | ✓ | ✓ |
| 取引先・活動 | ✓ | ✓ | ✓ | ✓ | ✓ |
| 人事業務 | ✓ | ✓ | — | — | — |
| 用户管理 | ✓ | — | — | — | — |

**营业保存社員时**：后端 `applySalaryWritePermission` 会忽略薪资/人事字段变更，保留数据库原值；前端「給与・人事」Tab 为只读。

**HR 访问案件 API**：返回 HTTP 403；社员詳細的「案件・配属」Tab 与侧栏案件菜单均隐藏。

### 5.5 数据范围（DataScopeService）

员工检索、详情访问、登记时的部门选择均受 `visibleDepartmentIdsOrNull()` 约束。`null` 表示无部门限制（全社）。

| 角色 | 可见社員范围 | 可登记部门范围 |
|------|-------------|----------------|
| ADMIN / HR | 全社 | 全部門 |
| SALES_HEAD | 全部門（**除人事部**） | 同左 |
| DIVISION_HEAD | 本事业部 + 子部门 | 子部门（无子部门时为本部门） |
| DEPT_HEAD | 本部门 | 本部门 |

人事部名称固定为 `人事部`，営業部固定为 `営業部`（与角色绑定）。

## 8. 业务流程设计

### 8.1 案件状态流转

```
新建 ──► OPEN（募集中）
           │
           │ 候補者採用確定（自动）
           ▼
    PARTIALLY_FILLED（一部確定）◄──┐
           │                      │ 配属取消（自动回退）
           │ 人数已满              │
           ▼                      │
       FILLED（満員）──────────────┘

手动：ON_HOLD / CLOSED / CANCELLED
```

- **自動**：OPEN ↔ PARTIALLY_FILLED ↔ FILLED（由 headcount_filled 驱动）
- **案件マッチング**仅 OPEN、PARTIALLY_FILLED 可用

### 8.2 候補者选考流程

```
案件マッチング → 候補追加（MATCHED）→ PROPOSED → INTERVIEWING
    → 採用確定（CONFIRMED）→ 配属 PLANNED → headcount_filled +1
终态：REJECTED / WITHDRAWN / LOST
```

### 8.3 案件匹配逻辑

1. 前端组装案件文本或选择已有案件
2. `ProjectInfoParser` 解析技能・単価・关键词
3. 合并 DB 结构化字段
4. `ProjectMatcher` 对范围内社員技能 token、単価、稼働状态打分排序

### 8.4 人事業務

- **証明書/申請書**：前端 HTML 预览 → 印刷/PDF
- **申請書確認**：上传 .docx → 人事确认 → PDF 保存、稼働状況更新
- **給与明細**：从社員薪资生成明細 → 保存至ファイル管理
- **取引先送付**：选择附件 + SMTP 发送（`app.mail.enabled=true`）

### 8.5 ファイル管理

- 分类：勤務表、申請書、給与明細等
- 批量上传可触发 `TimesheetAttendanceSyncService` / `ExpenseApplicationSyncService`

### 8.6 社員状态自动维护

- 定时任务（默认 01:30 JST）
- 生成 `employee_status_suggestion`
- 有案件编辑权限者在「状態提案」画面 apply / dismiss

### 8.7 総合評価与雷达图

- 评价项录入后 `EvaluationCalculationService` 同步计算综合排名
- 詳細页「総合評価」Tab：左侧分类表 + 右侧 SVG 雷达图（`EvaluationRadarChart`）

## 10. 非功能需求与运维

### 10.1 安全

- Session 认证 + 可选 MFA（TOTP + 恢复码）
- 分层权限（社員 / 薪资 / 案件 / 文件 分离）
- 部门数据范围（DataScopeService）
- 审计日志（登录、CRUD、文件、案件关键操作）
- 本番必须修改默认密码；建议内网访问 + HTTPS 反代

### 10.2 性能与容量

| 项目 | 现状 | 12～15 用户评估 |
|------|------|----------------|
| 架构 | 单体 JAR + 单 PostgreSQL | 足够 |
| DB 连接池 | Hikari max 15 | 足够 |
| 水平扩展 | 未实现（Session 内存） | 当前规模不需要 |
| 重操作 | 案件匹配、批量文件 | 错峰使用即可 |

建议生产服务器：**2 核 4GB 起**（Docker），推荐 4 核 8GB。

### 10.3 备份

- 数据库：`pg_dump`（见 deploy-linux.md / deploy-docker.md）
- 文件：Docker 卷 `employee-files` 定期归档
- 勿随意 `docker compose down -v`

### 10.4 初始账号（空库自动创建）

| 用户名 | 密码 | 角色 |
|--------|------|------|
| admin | admin123 | ADMIN |
| hr | hr123 | HR |

**本番环境必须立即修改密码。** 通过「用户管理」创建营业/事务真实账号。

### 10.5 PostgreSQL 连接（默认）

```
jdbc:postgresql://localhost:5432/employee_mgmt
用户: employee_app
连接池: maximum-pool-size=15
```

Docker Compose 内应用通过服务名 `postgres` 连接。
